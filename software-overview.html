Software Environment

The HAR Distributed Framework relies on a software stack that supports wearable sensor acquisition, embedded neural network inference, distributed communication, synchronization, experiment logging, and real-time visualization.

Because the framework operates across multiple embedded computing devices, the software environment must also provide a consistent mechanism for deploying and executing the required components on independent nodes.

The principal software technologies used by the framework include:

  • Linux-based operating environments on the NVIDIA Jetson platforms;
  • Docker for containerized deployment;
  • ROS Noetic for distributed communication;
  • Python for data acquisition, inference, communication, and experiment utilities;
  • PyTorch for neural network inference;
  • NVIDIA CUDA support for GPU-accelerated inference where applicable;
  • Chrony for network clock synchronization; and
  • Unity for the real-time visualization interface.

Not every component is executed on every device.

The edge nodes primarily execute sensor acquisition and local inference, while the central node executes synchronization, prediction fusion, experiment logging, and communication with higher-level visualization components.

Distributed Software Roles

The software responsibilities are distributed according to the role of each computing node.

Edge Nodes

Each edge node is responsible for running the software required to:

  • communicate with its associated wearable sensor;
  • acquire incoming sensor measurements;
  • buffer sensor data;
  • construct input windows;
  • execute a local HAR neural network;
  • generate activity probability vectors;
  • publish predictions through ROS;
  • timestamp prediction messages; and
  • record local performance information when required.

Conceptually:

Linux
  │
Docker
  │
ROS + Python + PyTorch
  │
  ├── Sensor Acquisition
  ├── Data Buffering
  ├── Local Inference
  └── Prediction Publisher

Central Node

The central computing node executes the software responsible for:

  • receiving predictions from all distributed nodes;
  • synchronizing incoming prediction messages;
  • handling temporarily unavailable predictions;
  • executing the central fusion model;
  • publishing global predictions;
  • recording timing and synchronization metrics; and
  • communicating with the visualization interface.

Conceptually:

Linux
  │
Docker
  │
ROS + Python + PyTorch
  │
  ├── Prediction Subscribers
  ├── Synchronization
  ├── Fusion Model
  ├── Global Prediction
  └── Experiment Logging

Containerized Deployment

Docker is used to provide isolated and reproducible execution environments across the distributed embedded devices.

Rather than configuring every framework dependency directly in the host operating system, the main runtime components can be executed inside containers.

The general deployment structure is:

Jetson Host System
       │
       ▼
     Docker
       │
       ▼
HAR Container
       │
       ├── ROS Noetic
       ├── Python
       ├── HAR Software
       ├── Model Files
       └── Required Dependencies

Containerization provides a consistent software environment across different computing nodes and simplifies deployment of the distributed ROS-based system.

The exact Docker configuration, container creation procedure, device access, networking options, and execution commands are documented separately.

ROS Noetic

The distributed communication layer is implemented using ROS Noetic.

ROS provides the publish/subscribe infrastructure used to exchange prediction information between the five local edge nodes and the central computing node.

The communication architecture follows the general structure:

Local Edge Nodes
      │
      │ ROS Topics
      ▼
Central Node
      │
      ▼
Global Prediction

Each local node publishes its probability predictions through a dedicated ROS topic.

The central node subscribes to the distributed prediction streams and processes them as part of the synchronization and fusion pipeline.

ROS is also used to distribute control and visualization-related information within the framework.

Detailed documentation of the ROS architecture is provided later under the Communication Framework section.

Python Environment

Python is used extensively throughout the implementation of the distributed system.

Python-based components support tasks including:

  • wearable sensor communication;
  • sensor data handling;
  • local inference;
  • model loading;
  • ROS publishers and subscribers;
  • prediction synchronization;
  • central fusion;
  • experiment logging;
  • performance analysis; and
  • supporting utilities.

The precise Python version and package requirements depend on the Jetson software environment used for each deployment.

For reproducibility, package versions and installation procedures should be documented alongside the corresponding container or execution environment.

PyTorch

The neural network models used by the framework are implemented and executed using PyTorch.

PyTorch is used for:

  • loading trained model parameters;
  • preparing model inputs;
  • executing local neural network inference;
  • executing the central fusion model; and
  • GPU-accelerated inference where supported by the target platform.

A previously evaluated centralized GPU environment used:

PyTorch 2.0.0+nv23.05
CUDA 11.4

These versions correspond to that specific centralized deployment and should not automatically be assumed to represent every Jetson node in the distributed system.

The exact software configuration for each platform will therefore be documented independently where necessary.

Clock Synchronization Software

The framework requires synchronized system clocks because predictions are generated independently across multiple physical devices.

Chrony is used to maintain clock synchronization between the central node and the distributed edge nodes.

Conceptually:

                 Central Node
                 Time Reference
                      │
        ┌─────────────┼─────────────┐
        │             │             │
        ▼             ▼             ▼
     Edge 1        Edge 2        Edge 3
        │             │             │
        ▼             ▼             ▼
     Edge 4        Edge 5       synchronized
                                  timestamps

Synchronized timestamps are subsequently used by the communication and experiment measurement mechanisms.

The complete Chrony configuration will be documented as a dedicated procedure.

Visualization Software

A graphical visualization interface was developed using Unity.

The interface receives global HAR information from the distributed system and provides a real-time representation of system predictions.

The Unity interface is not required for the core HAR inference process but provides a useful mechanism for observing system behavior during real-time experiments.

Its installation, ROS connectivity, activity visualization, and animation configuration are documented separately.

Reproducibility Considerations

For a distributed embedded system, recording software versions is particularly important because compatibility may depend on the combination of:

  • Jetson hardware;
  • NVIDIA JetPack version;
  • Ubuntu version;
  • CUDA version;
  • Python version;
  • PyTorch build;
  • ROS distribution; and
  • container configuration.

For this reason, subsequent implementation pages will distinguish between software versions that were actually used in the experimental system and versions that may be compatible but were not explicitly evaluated.

This distinction is important for maintaining reproducibility of the original implementation.
